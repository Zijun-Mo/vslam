# vSLAM Evaluation Pipeline for 7-Scenes Dataset

## Overview of the Evaluation System Architecture

The `vslam_evals` module provides a ROS2-based evaluation framework to assess visual SLAM results against ground truth, with specific support for known datasets like TUM and 7-Scenes. The system is composed of modular nodes orchestrated via a launch configuration:

- **Dataset Player Node**: For 7-Scenes, a custom node (`seven_scenes_player`) reads the dataset images from disk and publishes them as camera frames. It simulates the sequence playback, publishing images to `/camera/image_raw` at a controlled rate. After the last frame, it signals completion by publishing an empty message on `/dataset_done`. The player can wait for an explicit start signal (`/dataset_start`) before beginning playback.

- **vSLAM System Node(s)**: The main SLAM algorithm (launched via `vslam_system.launch.py`) subscribes to the image topic and performs visual SLAM. It produces real-time pose estimates, publishing optimized camera poses to a topic (e.g. `/vslam/pose_optimized`). In this setup, the SLAM system does not use a live camera feed but relies on the dataset player images (`use_video` is set to `false` in the launch).

- **Evaluation Node**: A dedicated node (`eval_node` in the `vslam_evals` package) listens to the SLAM’s output poses and compares them with ground truth at the end of the sequence. It subscribes to the SLAM pose topic and accumulates all estimated poses (with timestamps) internally. It also listens for the dataset completion signal and triggers the evaluation routine once the sequence is done. The evaluation node loads the ground truth trajectory for the sequence, aligns the estimated trajectory to ground truth, computes error metrics (Absolute Trajectory Error, ATE), and logs the results.

All these components are launched together. For example, the `eval_7scenes_office.launch.py` file includes the dataset player, the vSLAM system, and the eval node in one `LaunchDescription`, ensuring that they start and communicate properly. This architecture cleanly separates data playback, SLAM computation, and evaluation, which is beneficial for benchmarking and repeatability.

## Evaluation Flow Pipeline

The end-to-end evaluation process for a 7-Scenes sequence is orchestrated through ROS2 topics and callbacks. The flow can be summarized in several stages:

1. **Startup and Readiness:** When all nodes launch, the evaluation node waits for the SLAM system to signal it is ready. The SLAM system (or an associated helper node) publishes a boolean ready flag on `/vggt/model_ready` once essential initialization (e.g. loading maps or models) is done. The eval node subscribes to this topic. Upon receiving a `True` message (and if it has not already started), the eval node publishes an empty message on `/dataset_start`. This causes the `SevenScenesPlayer` to begin playback if it was configured to wait for the start signal. (The player’s parameter `wait_for_start` is `True` by default, meaning it idles until this signal arrives.)

2. **Dataset Playback and Pose Collection:** The `SevenScenesPlayer` node reads image files (e.g. `*.color.png` frames) from the specified sequence directory and publishes them as `sensor_msgs/Image` on `/camera/image_raw` at the specified frame rate. The effective playback rate is adjustable by a multiplier (`play_rate` parameter). For 7-Scenes, the source dataset is ~30 FPS, and `play_rate` default is `1.0` (real-time). The player uses a timer to publish each frame at interval `period = 1/(fps * play_rate)` seconds. It stamps each outgoing image message with an increasing timestamp (simulating the original timestamps of the sequence) and publishes it. As the SLAM system processes these images, it produces pose estimates. The vSLAM system publishes the **estimated camera pose** (position and orientation) for each frame on the topic `/vslam/pose_optimized` as a `PoseStamped`. The evaluation node is subscribed to this topic and stores each incoming pose in a list along with its timestamp. Each entry recorded is a tuple of time, position `(x, y, z)`, and orientation quaternion `(x, y, z, w)` for that frame’s estimated pose.

3. **Completion Signal and Ground Truth Loading:** When the dataset player has published the last frame, it invokes its `_finish()` routine which publishes a `std_msgs/Empty` message on `/dataset_done`. The evaluation node subscribes to this completion topic and thus is notified when the sequence is done. Upon receiving `/dataset_done`, the eval node waits a brief moment (in the code, a 10-second sleep) to ensure any last pose messages or final SLAM processing is completed before evaluation. It then proceeds to load the ground truth trajectory for the sequence from the provided `groundtruth_path`. The ground truth file is expected in the TUM RGB-D dataset format, i.e. each line contains a timestamp and the ground truth pose `(tx, ty, tz, qx, qy, qz, qw)`. The eval node’s `load_tum_trajectory` function reads this file, skipping comments (`#`) and parsing each line into a list of timestamped pose tuples. If the file is missing or empty, the eval node logs an error and aborts evaluation; otherwise, it obtains a list of ground truth poses.

4. **Temporal Alignment of Poses:** Before computing errors, the estimated trajectory must be time-aligned with the ground truth. The eval node sorts both the ground truth and estimated pose lists by timestamp. It then calls `associate_by_time(gt, est, max_diff)` to pair up poses that occur within a specified time window. The parameter `max_time_diff` (set to `0.01 s` in the 7-Scenes launch) defines the tolerance for considering two timestamps as a match. The association function iterates through each estimated timestamp, finds the nearest ground truth timestamp, and if the difference is `<= max_diff`, marks them as a matching pair. It ensures each ground truth pose is matched to at most one estimate by choosing the closest match and ignoring duplicates. The result is a list of index pairs linking ground truth and estimate positions that correspond in time. If no pose pairs can be associated (e.g. if timestamps are too misaligned), the eval node will log a warning and exit without computing errors.

5. **ATE Computation with Alignment:** With time-associated pose pairs, the eval node extracts the position components `(x, y, z)` of the matched poses to compute the **Absolute Trajectory Error (ATE)**. Before computing errors, it can align the estimated trajectory to the ground truth trajectory. In this implementation, alignment is done via a least-squares rigid transform (the **Umeyama method**), optionally allowing a scale adjustment. The launch file sets `align_scale: True` for 7-Scenes, meaning a **similarity transform (Sim3)** alignment is performed (scale + rotation + translation) to best fit the estimated points to ground truth. Internally, `compute_ate(...)` calls `umeyama_alignment(est_xyz, gt_xyz, with_scale=True)`. The `umeyama_alignment` function estimates the rotation `R`, translation `t`, and scale factor `s` that minimize the mean squared error between the transformed estimated points and the ground truth points. If scale alignment is enabled, it computes the optimal scale by comparing the variance of the point sets. The result is applied as `est_aligned = s * R * est_xyz + t`. If alignment were disabled, the raw estimated coordinates would be used as-is for error calculation. Finally, the ATE for each pose is computed as the Euclidean distance between the aligned estimated position and the ground truth position, yielding an array of per-frame translation errors (in meters).

6. **Error Metrics Calculation:** From the per-frame ATE values, the eval node computes summary statistics: Root Mean Square Error (RMSE), mean error, median error, standard deviation, and the maximum and minimum error observed. The RMSE is the primary metric, calculated as `sqrt(mean(error^2))` over all matched frames. These metrics provide a robust view of the trajectory accuracy — RMSE emphasizes larger errors, while mean/median give overall bias, and max/min bound the error range. The number of pose pairs `N` used in evaluation is also recorded (this is effectively the number of frames that were matched between estimate and ground truth).

7. **Logging and Output:** The evaluation results are both printed to console and saved to a CSV file. The console log from `EvalNode` reports `N` and the computed metrics, for example:

   ```text
   "[EvalNode] N=500, ATE_RMSE=0.142 m, mean=0.120, median=0.106, std=0.045, max=0.203, min=0.057"

In addition, the `eval_node` appends a line to a CSV file (default name `evals_7scenes.csv` for this launch) to facilitate aggregation of results across runs. The code writes a header on first use and then for each run writes a row with: sequence name, run ID, play rate, `N`, `RMSE`, `mean`, `median`, `std`, `max`, `min`. For example, the CSV header and an entry look like:

```text
seq_name,run_id,play_rate,N,rmse,mean,median,std,max,min
office/seq-01,run_001,1.0,500,0.142,0.120,0.106,0.045,0.203,0.057
```

The sequence name is taken from the parameter or inferred from the ground truth file path, and `run_id` is a user-set tag for the run (default `"run_001"`). The log file location is determined by the eval node: it attempts to place the CSV in the package’s `logs` directory (e.g. `<vslam_evals_package>/logs/evals_7scenes.csv`), creating it if necessary. If that fails (e.g., if running from a non-install context), it falls back to a `logs` folder in the current working directory. This ensures all evaluation runs are recorded for later analysis. Finally, after writing results, the eval node logs the completion and then shuts down the ROS node (calling `rclpy.shutdown()` internally).
